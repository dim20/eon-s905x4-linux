# v0.7-tty — the text console, as a product

The first release that ships the **text console** deliberately: a small
system with a login prompt on the television and the serial port as the
kernel console. There is no desktop in this image, and none is claimed.

It also carries the fix for the defect that made the previous images
unsafe to use with a framebuffer tool: opening `/dev/fb0` used to panic
the kernel twelve seconds later. On this kernel the same test runs three
times and returns clean.

## What changed since v0.6

### 1. The `/dev/fb0` panic is fixed — this is the reason to upgrade

v0.6 shipped a kernel whose framebuffer unmap path set
`info->screen_base = NULL` when the last user closed `/dev/fb0`, while
`fbcon` still owned that `fb_info` and its cursor timer kept drawing into
it. The next blink wrote through `NULL + offset`:

```
Workqueue: events_power_efficient fb_flashcursor
pc : cfb_imageblit+0x810/0x8c0
FAR : 0000000000000200        (a WRITE through a NULL screen base)
Kernel panic - not syncing: Fatal exception
```

Patch `0010` splits the unmap: a close drops its references and leaves
the mapping alone; only a replaced buffer or the framebuffer going away
clears `screen_base`. The test that panicked v0.6 — open, mmap, read and
close `/dev/fb0`, three times — now returns `rc=0` three times with no
panic and the box stays up.

### 2. The image contains no desktop, and says so

The v0.6 asset was *named* "desktop" but its package set contained no
desktop packages at all; the greeter its notes described came from the
test box's eMMC. That is written up as Correction 4 in
[`errata-v0.6.md`](errata-v0.6.md).

v0.7-tty is the same shape of system, now stated plainly: 271 packages,
`tasksel` present for the later optional-desktop work, and none of
`xfce4`, `lightdm`, `xserver-xorg` or `xinit`. The build refuses a tree
that contains them.

### 3. Our branding, not the vendor's

`/etc/issue`, `/etc/issue.net`, `/etc/eon-release` and the login-message
hooks are ours. The wordmark is plain ASCII — the framebuffer console
does not interpret escape sequences — and the login prompt ends with the
terminal name so you can tell `tty1` from `ttyS0`. No `qubian`, `quban`
or `devmfc` string survives in the branding files.

### 4. The vendor's leftovers are removed or masked

- the vendor's stick-growing script (`01-resize-rootfs`) is removed, so
  the stick stays 800 MB instead of rewriting its own partition table;
- `boot-run-once-early.service`, which ran it, is masked;
- `chronyd-restricted.service` is masked, so `chrony.service` — the one
  with the `RuntimeDirectory` — owns the port;
- `rsync.service` is masked: rsync ships as a command, not a daemon.

### 5. The serial port is the kernel console; the VT is the screen

`console=tty0` is gone from all four places the command line is written.
The kernel's log goes to serial, `getty` on `tty1` puts the prompt on the
television, and the vendor's `mem_free_work` line at 62 s no longer
appears in the middle of the login screen.

### 6. Patch `0009` is dropped, because its reason was false

`0009` commented out the vendor's delayed `mem_free_work`. Its stated
justification — the free pulls the memory out from under the display and
the box dies every minute — did not survive testing: a kernel without the
patch ran two hours past the free with the console on the display. With
`0005` stopping the OSD framebuffers being registered, nothing in the
image scans that memory. By this project's rule a patch with no true
reason goes, so it went. The 8 MB free happens again at 62 s and nothing
minds.

### 7. The kernel is an installable package, with rollback

`v0.7-tty-kernel.deb` installs the kernel and device tree to the boot
partition under a versioned name, keeps the previous one, backs up the
U-Boot environment first, and verifies every write by reading it back
from storage. `eon-kernel-list` shows what is installed and what can be
rolled back to. See [`../kernel-package.md`](../kernel-package.md).

### 8. The build and the installer learned what they were checking

- `build-stick-image.sh --check` stages the tree, applies the overrides,
  builds the boot partition and runs the manifest, without composing an
  image. It is the fast answer to "is this tree buildable?".
- The overrides loop installed a `README.md` into `/etc/systemd/system/`
  as if it were a unit; it now installs only names that look like units.
- `install-to-emmc.sh` expected the v0.5.x kernel (`93420f6a…`) and would
  have refused to install the current one. It now expects `45a67743…`.
- The installer's rsync excluded the SSH private keys but kept the
  vendor's `ssh_host_keys_ready` marker; `ssh.service`'s `ExecCondition`
  skips generation when that marker exists, so an installed eMMC would
  have had no host keys and sshd would have failed. The whole
  `ssh_host_*` set is excluded now, marker included.

## What is not fixed

- **The desktop.** It is frozen, not abandoned, and returns as an
  optional package set. `tasksel` will install one, and its text will be
  wrong for the reason in Correction 1 of the errata.
- **Audio.** The ASoC card registers and the HDMI transmitter reports a
  valid format; nobody has heard a speaker.
- **WiFi.** No open driver for the RTL8812CS; it needs a user-supplied
  vendor driver.
- **HDCP.** Each boot logs about twelve HDCP lines ending in
  `TX no hdcp key`: the vendor's HDMI TX has no HDCP key burned in. It is
  harmless for the framebuffer console and for anything this image
  displays. Recorded so it is not mistaken for a fault later.
- **U-Boot networking.** Recovery over U-Boot's network stack is broken
  on this board (wrong MAC). Recovery is the stick or the serial tools.
- **The published password.** `root` / `tvbox`. Change it with `passwd`
  before exposing the box to a network you do not trust.

## Last verified

**2026-10-23**, on the development box (EON SDSTB02, S905X4), running
from **eMMC p2** with the USB stick removed:

- cold boot from eMMC, text console on the television;
- login on the TV, commands run, `Ctrl-Alt-F1`…`F6` switching;
- `reboot` and `poweroff` behave; the front power button turns the box
  on again;
- `findmnt -n -o SOURCE /` → `/dev/mmcblk0p2`, 0 failed units,
  `apt-get check` clean, 271 packages;
- the kernel on p1 is `45a67743…`, matching `kernel/SHA256SUMS`.

The eMMC system was provisioned from the running stick with the fixed
installer. The **image file itself** has not yet been written to a stick
and booted; do that once before treating the download as exercised
end-to-end. The content is the same set of transforms, but the p1 FAT
layout and `aml_autoscript` are only proven by a stick boot.
