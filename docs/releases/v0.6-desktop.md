# v0.6-desktop — a desktop on the television

The first release with a **graphical desktop**. The LightDM greeter comes
up on the television, and XFCE with it.

It also contains the first **reproducible** build: the same tree now
gives the same image, byte for byte, so the image's hash is a statement
about its content rather than about when it was built.

## What changed

### 1. The desktop works — the blocker was not the vblank bug

The whole plan said the desktop was blocked by the vendor CRTC's missing
vblank interrupt. **It was not.** Xorg was running happily, reporting no
errors, and the television was black. The DRM debugfs said why:

```
plane[31]: osd0
    crtc=VPP-0
    fb=105
        allocated by = Xorg
```

Xorg was drawing into the **OSD overlay plane**. The picture on this box
comes from the VPU's own scanout path; the OSD is an overlay composited
by hardware, and it is **not CPU-accessible** — so X was painting into
memory that could not reach the screen.

There were two sets of "OSD FB" devices, from two different places, and
both had to stop being registered:

| | where | fix |
|---|---|---|
| the DRM driver's framebuffers for the OSD planes | `drivers/amlogic/drm/meson_fbdev.c` | `patches/0005` |
| the vendor's OSD **media** driver's framebuffers | `drivers/amlogic/media/osd/osd_fb.c` | `patches/0005` |

`CONFIG_AMLOGIC_MEDIA_FB` cannot simply be turned off — the DRM's logo
code and the video composer both need symbols from that driver, and the
link fails without it. The lever is the `register_framebuffer()` call.

### 2. The X server is driven through the framebuffer, not modesetting

The vendor's own `xorg.conf` asks for the modesetting driver, which
picks one of the OSD planes — the ones that cannot be read or written.
The image now ships its own `xorg.conf` that uses the fbdev driver
instead, which is the path the text console uses and the one that is
known to work.

### 3. The font cache is built before anything graphical starts

fontconfig builds its cache the first time something asks it for a font,
and until it is built it answers with a two-pixel default. The first
terminal's window came out **173×62 pixels for 80×24 characters** and the
text was a one-pixel smear — a black box.

The image now ships `fontconfig-cache.service`, which runs before the
display manager, so the first terminal a user opens is the right size.

### 4. The build is reproducible

The kernel embeds its build time, so two builds of the same tree produced
two different kernels — and therefore two different images. The stick
image build was reproducible; that was worthless, because the kernel
inside it was not.

`build-kernel.sh` now pins `KBUILD_BUILD_TIMESTAMP`,
`KBUILD_BUILD_VERSION`, `KBUILD_BUILD_USER` and `KBUILD_BUILD_HOST` from
`SOURCE_DATE_EPOCH`, which the kernel's own build scripts already honour.
Two builds with the same stamp now give a byte-identical kernel.

### 5. The image carries the manifest and the inventory

`manifest/` says what the image must contain and what it must not, and
the build checks the image it has just produced against it and refuses
to produce one that fails. `manifest/inventory.txt` lists every file with
its owner, mode, size and checksum, and every build prints the
difference against the last one.

The change from v0.5.1 to this release is, in full:

```
2 added, 0 removed, 0 changed
  + etc/X11/xorg.conf
  + etc/systemd/system/fontconfig-cache.service
```

## What was verified

1. The image was built **twice** from the same tree: byte-identical.
2. The image was checked against the manifest: it passes.
3. The image was written to the stick and read back: byte-identical.
4. The stick booted, and **the LightDM greeter came up on the television**.
5. The installer ran from the stick: content copied, environment restored
   and verified, the conditional boot command set and verified, boot
   artefacts verified, `e2fsck` clean.
6. The stick was unplugged and the box was power-cycled: it booted the
   eMMC on its own, with **zero failed units**, and `chrony` synchronised
   ("Leap status: Normal").

## Known limitations

- **Some windows' contents do not reach the display.** The X server's
  window content is correct — `xwd` shows the text — and it is in
  `/dev/fb0`, but the display shows a stale frame, and the mouse pointer
  vanishes over such windows. A *write* to the framebuffer does reach the
  display; an `mmap` write from the X server does not, and the X server
  makes no ioctl or fsync calls at all while drawing. The next step is to
  find what a write does that an mmap write does not — the damage path
  (`drm_fb_helper_dirty`) or the vout's framebuffer update — and make
  the mmap path do it too. The fbdev's own `.fb_sync` callback is a stub
  that does nothing, which is almost certainly wrong and is a good place
  to start looking.
- **The vblank interrupt is still broken.** The vsync IRQ fires at 61 Hz
  and the handler is correct, but the vendor's CRTC never delivers a
  vblank *event* to the X server, so anything that waits for one — the
  vendor's own `xorg.conf` with `Dri2Vsync true` — will time out. The
  fbdev path does not need a vblank, which is why it is the one we use.
- **The root password is published.** It is in a public repository, so
  anyone who plugs a display into an unconfigured box gets a root shell.
  The fix — ship the account locked and put a setup screen on the
  television on the first boot — is written up and is the next release.
- **The rootfs is still the vendor's**, with our changes on top. It
  should be built from a package list instead; that is parked, with the
  reasoning recorded, because it is a rewrite of something that works.
- **WiFi has no driver.** The kernel we ship enables no Realtek driver
  at all, so the chip needs one built before it can work.
- **Audio is unverified.** The ASoC card and SPDIF register, and nobody
  has heard a sound.
- **One box.** Nothing has been validated on other hardware.
