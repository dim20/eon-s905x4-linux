# v0.5-manifest — the image now says what it contains

The headline of this release is not visible on the television. It is that
the **build has a record**, and the build **checks itself**.

It also fixes three things that were wrong in v0.4, two of which the
record found and one of which it exposed.

## What changed

### 1. The image has a manifest, and the build checks it

`manifest/` is a set of plain-text files saying what the image must
contain and what it must not:

| file | what it states |
|---|---|
| `required-packages.txt` | the packages the image must contain |
| `forbidden-packages.txt` | no desktop, no display manager, no X server |
| `required-paths.txt` | the files it must contain, with their modes |
| `forbidden-paths.txt` | the machine-id, the SSH host keys, the vendor's login hooks, the vendor's stick-growing script, `/run` |
| `required-units.txt` | the systemd units it must have enabled |
| `global.txt` | rules for the whole rootfs |
| `boot-artifacts.txt` | what must be at the **root** of the boot partition |
| `inventory.txt` | every file in the image, with owner, mode, size and checksum |
| `provenance.txt` | where the rootfs came from, and what we changed on top |
| `vendor-leftovers.txt` | what is still the vendor's, and what it costs |

The build runs `scripts/check-image.sh` against the image it has just
produced and **refuses to produce an image that fails**. You can run it
by hand against any rootfs tree.

This matters because the requirements used to exist only as scattered
`if` statements inside the build script, and they were checked against
the *input*, not against the shipped bytes. A defect introduced while
assembling the image would have passed.

### 2. The build no longer modifies its own input

The build used to chown the rootfs tree, empty its `/run`, delete its
machine-id and replace its login-message hooks **in the tree itself**. So
the tree was an output that got reused as the next input: building twice
was not the same as building once, and there was no way to tell what the
tree looked like before a build.

It now copies the tree to a scratch directory and works on the copy. The
tree you give the build is exactly the tree you still have afterwards.

### 3. The build is reproducible

The same tree now gives the same image, **byte for byte**. Two builds
produce the same sha256, which makes the image's hash a statement about
its content rather than about when it was built.

Three things had to be pinned:

- `sfdisk` writes a **random disk identifier** into the MBR at offset
  440. It is now derived from the kernel's checksum, so it is stable for
  a given kernel and different for a different one.
- `mkfs.vfat` writes the **current time** into the volume label's
  directory entry. `mkfs.vfat --invariant` fixes it.
- `mcopy` writes the **current time** into each file's creation field.
  mtools honours `SOURCE_DATE_EPOCH`, so it does not.

The filesystem's timestamps and UUIDs were pinned too:
`E2FSPROGS_FAKE_TIME`, a fixed filesystem UUID, a fixed directory hash
seed, and `gzip -n`.

### 4. Ten packages had no file list in the dpkg database

The record found this. Ten packages in the v0.4 image had **no
`/var/lib/dpkg/info/<package>.list`**, so dpkg did not know they owned
their files:

```
# dpkg -L libacl1
dpkg-query: warning: files list file for package 'libacl1' missing;
             assuming package has no files currently installed
```

`dpkg -L` printed nothing, `dpkg -S` could not find the owner, and dpkg
printed that warning every time it was asked about one of them.

It was **our own tooling**: `harvest-pkg.sh` copied the package's files
and its status stanza into the tree, but not dpkg's info files. It
copies them now, and the ten affected packages are repaired.

### 5. The stick does not grow any more

The vendor's image ships `/etc/boot-run-once/early/01-resize-rootfs`,
which runs `parted resizepart ... 100%` and `resize2fs` on the root
filesystem **on every boot**. On the stick that rewrites the partition
table and grows the filesystem to fill the device — which is why the
install source was "the whole stick" rather than 800 MB, and why the
installer had to copy the rootfs's *content* rather than its partition.
On the eMMC it repartitions the flash on every boot.

It is removed. The stick stays exactly the image we published, and
`scripts/grow-stick.sh` grows it when you want it grown, on purpose.

### 6. `enable-hdmi.service` is enabled

The unit that programs the HDMI output at boot was in the image but not
switched on, so it never ran. It is now enabled. (The DRM driver sets a
mode when the console binds to the framebuffer, so this is belt and
braces — but it is what covers the case where the console does not bind,
and it is what the rescue path relies on.)

## What did not change

- The kernel and the device tree: the same ones as v0.4.
- The installer: unchanged.
- The text console on the HDMI output: unchanged, and still the thing
  that makes this a usable computer.
- No desktop, no display manager: still not in the image. `tasksel` is
  still how you choose one.
- The published root password is still `tvbox`. **This is the next
  release's job** — see below.

---

## What was verified

1. The image was built **twice** from the same tree, and the two were
   compared byte for byte: identical.
2. The image was checked against the manifest: it passes.
3. The build does not modify its input tree: confirmed by building
   twice and diffing the tree.

*(the hardware checklist is in `dist/TEST-CHECKLIST.md`; the results of
the box test are added below when it has been run)*

## Known limitations

- **The root password is published.** It is in a public repository, so
  anyone who plugs a display into an unconfigured box gets a root shell.
  The fix — ship the account locked and put a setup screen on the
  television on the first boot — is written up and is the next release.
- **The rootfs is still the vendor's**, with our changes on top. It
  should be built from a package list instead; that is parked, with the
  reasoning recorded, because it is a rewrite of something that works.
- **WiFi has no driver.** The kernel we ship enables no Realtek driver
  at all, so the chip needs one built before it can work.
- **Audio is unverified.** The ASoC card and SPDIF register, and nobody
  has heard a sound.
- **One box.** Nothing has been validated on other hardware.
