# v0.5.1 — zero failed units

A maintenance release. The image is the same Debian system as v0.5, with
the same kernel, and it fixes three things that v0.5 got wrong.

If you are new here, read [v0.5-manifest](v0.5-manifest.md) first: that
is the release that gives the image a manifest, an inventory, a build that
does not modify its own input, and a build that is **reproducible** — the
same tree gives the same image, byte for byte.

## What changed

### 1. The box now boots with **zero failed units**

v0.5 booted with one failed unit and called itself "degraded". Two more
were hiding behind it. The cause was the same in all three cases, and it
is worth understanding, because it is not obvious.

**Debian's preset policy puts units back.** A unit that ships a SysV init
script is enabled by
`/usr/lib/systemd/system-preset/50-debian-systemd.preset`, and systemd
applies that policy **at every boot**. So removing a unit's symlink from
the image does not stop it: it comes back on the next boot, silently.

That is not a theory. On the box, `chronyd-restricted.service`,
`chrony-wait.service` and `rsync.service` all reappeared after they had
been removed from the image, and `systemctl preset-all` recreated all
three of them on demand.

**The fix is to mask the unit** — a symlink to `/dev/null` in
`/etc/systemd/system`. A masked unit cannot be started, and the preset
policy ignores it ("Unit … is masked, ignoring"). That is the
systemd-native way to say "this unit must not run", and it survives every
boot.

The three units now masked:

| unit | why |
|---|---|
| `chronyd-restricted.service` | the vendor's second NTP daemon. It takes port 323 from `chrony.service`, which is the one the manifest requires — and which then sits there *enabled, present, and not running* |
| `boot-run-once-early.service` | it ran the scripts in `/etc/boot-run-once/early`, which was the vendor's stick-growing script and nothing else. Its post-step is `chmod -x /etc/boot-run-once/early/*`, which fails when that directory is gone, and the unit fails with it |
| `rsync.service` | the rsync **daemon**. We ship rsync as a command, not a server. It never starts (it wants `/etc/rsyncd.conf`), but "enabled and not running" is exactly the state we are trying to get rid of. Unmask it if you want the daemon. |

`chrony.service` now runs, selects a source and reports
`Leap status: Normal`.

### 2. `systemd-remount-fs` failed at every boot

v0.5 made the image **reproducible**, and one of the things that had to be
pinned was the filesystem's UUID. But the tree's `/etc/fstab` names the
root filesystem by the UUID it had when the tree was made — so the fstab
pointed at a filesystem that did not exist, `systemd-remount-fs` could not
find it, and the unit failed. The root filesystem was also left with the
kernel's default mount options instead of the ones in the fstab.

The build now writes the fstab, with the image's own UUID and the boot
partition's own volume serial. Both are fixed, so the fstab is
deterministic too.

### 3. `manifest/` learned about masks and about forbidden units

Two new files, and the checker understands them:

- `manifest/masked-units.txt` — the units that must be masked.
- `manifest/forbidden-units.txt` — the units that must not be enabled.

The distinction matters: "not enabled" does not survive a boot on its
own, and the manifest now says which of the two it means.

## What was verified

The automated part:

1. The image was built **twice** from the same tree and compared byte for
   byte: identical.
2. The image was checked against the manifest: it passes.
3. The inventory diff for this build is exactly the four intended
   changes and nothing else:

```
ADDED
  + etc/fstab                                   (the new one)
  + etc/systemd/system/boot-run-once-early.service  -> /dev/null
  + etc/systemd/system/chronyd-restricted.service    -> /dev/null
  + etc/systemd/system/rsync.service                -> /dev/null
REMOVED
  - etc/fstab                                   (the old one)
  - var/lib/systemd/deb-systemd-helper-enabled/chronyd-restricted.service.dsh-also
  - etc/systemd/system/boot-run-once-early.service
  - etc/systemd/system/sysinit.target.wants/boot-run-once-early.service
```

The part that needs a box, a stick and a television:

4. The image was written to the stick and read back: **byte-identical**.
5. The stick booted: the console took the framebuffer over, bound to the
   DRM device, 240x67. Zero panics, zero vblank timeouts, **zero failed
   units**.
6. The stick did **not** grow: its second partition is 838,860,800 bytes,
   exactly the size of the image.
7. The installer ran from the stick: content copied, the environment
   restored and verified, the conditional boot command set and verified,
   the boot artefacts verified, `e2fsck` clean.
8. **The stick was unplugged and the box was power-cycled.** With nothing
   plugged in it booted the eMMC on its own: the console came up on the
   television, there were **zero failed units**, `chrony.service` was
   active and synchronised (`Leap status: Normal`, 1.3 ms from NTP time),
   and sshd was up.

## Known limitations

- **The root password is published.** It is in a public repository, so
  anyone who plugs a display into an unconfigured box gets a root shell.
  The fix — ship the account locked and put a setup screen on the
  television on the first boot — is written up and is the next release.
- **The rootfs is still the vendor's**, with our changes on top. It
  should be built from a package list instead; that is parked, with the
  reasoning recorded, because it is a rewrite of something that works.
- **WiFi has no driver.** The kernel we ship enables no Realtek driver at
  all, so the chip needs one built before it can work.
- **Audio is unverified.** The ASoC card and SPDIF register, and nobody
  has heard a sound.
- **One box.** Nothing has been validated on other hardware.
